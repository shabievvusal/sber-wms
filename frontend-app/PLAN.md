# ZLP — план модернизации

> **Объединение репозиториев (2026-07-15)**: эта папка физически
> переехала из отдельной сиблинг-папки `new zlp` в `frontend-app/` внутри
> `new zlp-backend` (по просьбе пользователя — единая папка для заливки
> на GitHub). Все относительные пути ниже (`.`, `../zlp-main-main`)
> исторические — писались, когда эта папка ещё была самостоятельным
> сиблингом бэкенда, а не его подпапкой; не переписывались задним числом.
> Подробности объединения — `new zlp-backend/PLAN.md` (шапка файла).

Общий трекинг для двух версий проекта:
- `../zlp-main-main` — текущий прод (Node/Express + React, не трогаем).
- `.` (`new zlp`) — песочница нового фронтенда, потом и нового бэкенда.

Не документ для одной сессии — обновляем по ходу, чтобы не терять контекст между заходами.

## Главный принцип (сказано явно, не забывать)

> JS — **только** для парсинга данных из браузера с `wwh.samokat.ru` (там нужна
> сессия/токен пользователя, сервер сам сходить не может). Всё остальное —
> бизнес-логика, подсчёты, API — переезжает на более современный и
> производительный для продакшна стек. JS не должен быть языком, который
> «делает вообще всё» — сейчас в проекте это так, и это и есть корневая проблема.

## Трек 2 — Бэкенд: замена Node/Express (Фаза 0 сделана, 2026-07-12)

**Решение:** ASP.NET Core (C#) вместо Node/Express.
**Почему:** в проекте уже 5 .NET-тулов (`tools/ArticleSpeeds`, `EmployeePerformance`,
`MissingWeightRebuild`, `WeightScan`, `SaveFetchedData`), .NET runtime уже в
Docker-образе — не четвёртый язык в стеке, а объединение API и тяжёлых
вычислений в одном рантайме.

**Стратегия миграции:** постепенно, эндпоинт за эндпоинтом (strangler fig), не
рывком. Node остаётся в проде рабочим на всё время миграции.

**Организационный момент**: `backend/`, `docker-compose.yml`, `Dockerfile` —
часть оригинала (`zlp-main-main`), который нельзя трогать (то же правило, что
и весь фронтенд-трек). Поэтому вся работа по Треку 2 идёт в отдельной новой
песочнице **`b:\рабочий стол\new zlp-backend`** (сиблинг `zlp-main-main` и
`new zlp`, скопирован `backend/`+docker-файлы+`tools/`, оригинал не менялся).
Подробности, разведка и обоснования решений — в `new zlp-backend/PLAN.md`,
здесь только чек-лист по фазам.

### Живая верификация (2026-07-12) — Docker Desktop оказался доступен

В рабочем окружении неожиданно обнаружился запущенный Docker Desktop —
впервые за все три фазы получилось реально собрать (`docker compose up
--build`) и прогнать C#-код через Caddy, а не только вычитать его. **Само
по себе построчное ревью не поймало 3 реальных бага** — их поймало только
исполнение:
1. Конфликт версий NuGet-пакетов (`Npgsql`/`Microsoft.EntityFrameworkCore`)
   блокировал сборку целиком (NU1605).
2. `SqlQueryRaw<T>` в EF Core 9 требует, чтобы скалярная колонка называлась
   ровно `"Value"` — падали `/api/dotnet-status` (Фаза 0/1) и
   `TsdService.GetSettingsAsync()` (Фаза 2).
3. `RouteService.cs` держал `static readonly CultureInfo Ru = new("ru-RU")`,
   а `.csproj` включал `InvariantGlobalization=true` — падали ВСЕ маршруты
   с русской сортировкой (`/api/rk/drivers`, `/api/rk/cfz`,
   `driver-rokhlya-debt`), то есть Фаза 1 была нерабочей целиком в проде,
   несмотря на одобрение при ревью.

Все три исправлены. Позже нашёлся и **4-й баг — уже инфраструктурный**:
`.env`'s `PORT` (задуман только как внешний хост-порт для caddy) протекал
через `env_file: .env` внутрь контейнера `node`, и `server.js` слушал
именно его — из-за чего node слушал 3007 вместо жёстко зашитого в
`Caddyfile` `node:3009`, и Caddy получал `connection refused`. Исправлено
явным `environment: - PORT=3009` у сервиса `node` в `docker-compose.yml`
(перекрывает `env_file` для этой переменной).

После всех фиксов вручную через `curl` подтверждены рабочими: TSD
(assign/return/return-tsd с `foreignReturn`/settings/гейтинг сессией/
валидация), Employees (создание/чтение с кириллицей, `add-new`, `POST
/api/employees` оба формата), Routes (импорт WMS-JSON → JSONB round-trip →
ship/receive → confirm-ship/confirm-receive → `WithTotals`/`diff`/
`rokhlyaDebt` → агрегации по водителям/ЦФЗ с верной русской сортировкой →
фильтры `GET /api/rk/routes` → оба `DELETE`-маршрута), и **центральная
проверка Фазы 2** — статистика (`/api/date/:date/summary?shift=`,
`/api/stats/monthly-company`, `/api/stats/monthly-employees`) и
консолидация (`PUT .../lookup`) корректно резолвят компанию сотрудника
через новый бескэшевый `getCompanyLookupMaps()`/`getCompanyByIdOrFioSync()`
— то самое место, которое было отмечено как самая рискованная правка

## Из security/архитектурного аудита — не забыть поправить по пути

(Полный список был озвучен раньше в разговоре; ключевое — то, что нужно не
потерять при переписывании бэкенда, а не откладывать «на потом».)

- **Незащищённые write-эндпоинты**: `POST /api/date/:date/storage`,
  `POST /api/stats/send-hourly-telegram`, `send-idles-telegram` — висят на
  `vsSessionOptional`, но не проверяют сессию внутри. При переносе на .NET —
  сразу закладывать нормальную авторизацию, не копировать баг.
- **Нет rate-limit на логине** (`POST /api/vs/auth/login`) — при переписывании
  auth в конце миграции добавить лимитер. **Всё ещё не сделано**: Фаза 4
  (2026-07-13) перенесла `/api/vs/auth/login` на dotnet дословно (порт
  логики, не редизайн — тот же принцип, что и везде в треке), лимитер не
  входил в подтверждённый пользователем объём фазы. Поднять отдельно, если
  актуально.
- **`statsCalc.js` дублирует `storage.js`** (функция `addWeight` один в один) —
  фронт пересчитывает то, что должен только отрисовывать. Решится само, когда
  агрегации переедут на бэкенд (см. Трек 2, «Статистика/агрегации»).
- **Один статичный `NODE_TOKEN`** для `/api/node/*` (kill-switch ноды, удаление
  проекта на хосте) — большой blast radius, нет audit-лога вызовов. Не менять
  архитектуру без обсуждения (это бизнес-модель лицензирования), но при
  переезде на .NET добавить логирование каждого вызова.
- **`docker-compose.yml` монтирует `/var/run/docker.sock`** в контейнер — держать
  в уме при проектировании нового `backend-dotnet` сервиса, не тащить тот же
  монт без необходимости.
- **Маршрут `/` (Статистика) не гейтится модулем `stats`** (найдено при
  переносе `StatsPage`, 2026-07-12) — единственная из 20+ страниц оригинала,
  не обёрнутая в `ModuleRoute`: любой залогиненный видит раздел независимо от
  того, есть ли `stats` в его `user.modules`. Решение пользователя —
  задокументировать, не чинить сейчас. При переносе авторизации на .NET
  (Трек 2) решить осознанно: либо реально гейтить `/` тем же способом, что и
  остальные страницы, либо сознательно исключить `stats` из проверяемых
  модулей (и тогда убрать его из редактируемого списка прав в Settings, а не
  оставлять переключатель без эффекта).
